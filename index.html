CHAPTER 1 · 1강

🍽️ 메뉴 기획 — 뭘 팔 건데?

📋 어떤 요리를, 누구에게, 어떻게 팔지 정하기
💡

AI 기능을 만들었다고 서비스가 되는 건 아닙니다. 누가, 어디서, 어떻게 쓸 건지 정해야 진짜 서비스가 됩니다.

맛있는 파스타를 만들 줄 안다고 바로 레스토랑을 열진 않죠. "이 요리를 누가 먹을까? 배달로 팔까, 매장에서 팔까? 가격은?" — 이런 질문에 답하는 게 메뉴 기획이에요.

AI 서비스도 마찬가지입니다. 만든 AI 기능을 누가(사용자), 어떤 채널에서(웹? 앱? API?), 어떤 방식으로(채팅? 버튼?) 쓸 건지 정하고, 코드를 쓰기 전에 프로토타입으로 먼저 돌려보는 거예요. 실제로 만들기 전에 "이거 쓸 만한가?" 확인하는 거죠.

서비스 설계 체크리스트
# 서비스 기획 3대 질문 WHO → 타깃 사용자는? (개발자? 일반인? 기업?) WHERE → 어디서 쓰나? (웹앱, 슬랙봇, API, 모바일?) HOW → 어떻게 쓰나? (채팅형, 폼입력, 자동화?) # 프로토타입 먼저! → 코드 없이 Figma/노션으로 흐름 검증 → "이거 진짜 쓸 만해?" 확인 후 개발 시작
✅ 한 줄 정리: 코드부터 짜지 말고, "누가 어디서 어떻게 쓸 건지"부터 정하자.
CHAPTER 2 · 2강

🏪 가게 오픈 — 드디어 문을 열다

🔑 건물(GCP) 임대하고 간판(URL) 달기
💡

Google Cloud 계정을 만들고, gcloud CLI로 Cloud Run에 첫 배포를 합니다.

메뉴가 정해졌으니 이제 가게를 열 차례! 건물(Google Cloud)을 임대하고, 주소(프로젝트 ID)를 받고, 간판(서비스 URL)을 다는 거예요.

처음 가게 문을 여는 날, 긴장되지 않나요? Cloud Run에 첫 배포를 하면 진짜 인터넷에서 접속 가능한 URL이 생깁니다. "내가 만든 AI가 진짜 돌아가고 있다!"는 감동이 있어요.

첫 배포
# Google Cloud 프로젝트 설정 gcloud config set project my-ai-service gcloud config set run/region us-central1 # Cloud Run에 배포! gcloud run deploy friend-agent --source . ✓ Deploying... Done. Service URL: https://friend-agent-xxx.run.app 🎉 세상에 내 AI 서비스가 공개되었다!
✅ 한 줄 정리: gcloud run deploy 한 줄이면 AI가 인터넷에 공개된다.
💻

BEFORE

내 노트북에서만 돌아가는 AI

🌍

AFTER

URL 하나로 누구나 쓸 수 있는 서비스

CHAPTER 3 · 3강

👨‍🍳 주방 운영 — 주문이 밀리면?

⏱️ 셰프(인스턴스) 몇 명 둘까? 조리시간(타임아웃) 제한은?
💡

타임아웃, 인스턴스 수, 동시 요청 한도를 AI 서비스 특성에 맞게 설정합니다.

가게가 열렸는데 손님이 한꺼번에 몰리면? 셰프 한 명이 모든 주문을 감당할 수 없죠. 만약 파스타 하나에 30분이 걸린다면, 10분 만에 나가는 샐러드와 같은 타임아웃을 줄 수 있을까요?

AI 서비스는 일반 API보다 응답이 느립니다. LLM이 답을 생성하는 데 시간이 걸리거든요. 그래서 타임아웃을 넉넉하게 잡고, 긴 답변은 스트리밍으로 조금씩 보내야 합니다. 또 인스턴스 수를 조절해서 비용과 성능 사이 균형을 맞춰야 해요.

Cloud Run 설정
# AI 서비스에 맞는 설정 gcloud run deploy friend-agent \ --timeout=300 \ # 5분 (LLM은 느리다) --concurrency=4 \ # 인스턴스당 동시 4명 --min-instances=0 \ # 안 쓸 때는 0으로 절약 --max-instances=5 # 최대 5개로 비용 제한 # 답이 끊기는 문제? → 스트리밍! → SSE(Server-Sent Events)로 토큰 단위 전송
✅ 한 줄 정리: AI 서비스는 느리다. 타임아웃 넉넉히 + 스트리밍으로 체감 속도를 잡자.
CHAPTER 4 · 4강

🤖 배달 자동화 — 레시피가 바뀌면 자동으로

🔄 레시피(코드) 바뀌면 → 주방(서버)에 자동 전달
💡

PR을 머지하면 GitHub Actions가 자동으로 Cloud Run에 배포합니다. WIF로 키 파일 없이 인증.

레시피를 바꿀 때마다 사장님이 직접 주방까지 가서 전달하면 힘들겠죠? 컨베이어 벨트를 설치하면 레시피가 바뀌는 순간 자동으로 주방에 전달됩니다.

GitHub Actions가 바로 이 컨베이어 벨트예요. main 브랜치에 코드를 머지하면 자동으로 빌드→배포가 일어납니다. 그리고 Workload Identity Federation(WIF)를 쓰면 키 파일 없이도 GCP에 인증할 수 있어요. 열쇠를 안 들고 다녀도 되는 얼굴 인식 출입 시스템 같은 거죠.

deploy.yml
# GitHub Actions 워크플로 핵심 on: push: branches: [main] # main에 머지되면 자동 시작 jobs: deploy: - google-github-actions/auth # WIF 인증 (키 없음!) - gcloud run deploy # 자동 배포 → PR 머지 = 자동 배포 완료!
✅ 한 줄 정리: PR 머지 한 번이면 코드가 자동으로 서버에 올라간다.
🏃

BEFORE

코드 바꿀 때마다
직접 gcloud run deploy

AFTER

CHAPTER 5 · 5강 & 6강

🧪 위생 검사 — 상한 재료는 안 돼

📜 식약처 검사(CI) + 표준 레시피(Dockerfile)
💡

코드를 합칠 때마다 자동 테스트(CI)를 돌리고, Dockerfile로 실행 환경을 확실하게 정합니다.

레스토랑에 식약처가 와서 위생 검사를 하듯, 코드에도 검사가 필요합니다. 버그가 있는 코드가 서버에 올라가면? 손님들이 식중독에 걸리는 거나 마찬가지예요.

CI(Continuous Integration)는 코드를 합칠 때마다 자동으로 테스트를 돌려서 "이 코드 괜찮아?"를 확인합니다. 그리고 Dockerfile은 표준 레시피 — "이 재료, 이 순서, 이 온도로 만들어"라고 정확히 적어두는 거예요. 내 컴퓨터에선 되는데 서버에선 안 되는 문제를 막아줍니다.

Dockerfile + CI
# Dockerfile = 표준 레시피 FROM python:3.12-slim # 기본 재료 COPY requirements.txt . # 필요한 양념 목록 RUN pip install -r requirements.txt COPY . . # 레시피 전체 CMD ["uvicorn", "main:app"] # 조리 시작! # CI 파이프라인 = 위생 검사 pytest tests/ ✓ 3 passed ruff check . ✓ All checks passed
✅ 한 줄 정리: Dockerfile로 환경을 고정하고, CI로 매번 자동 검사하면 사고가 없다.
CHAPTER 6 · 7강

🏢 프랜차이즈 — 본점 레시피 그대로

📦 본점(staging)에서 검증한 레시피를 지점(production)에 그대로
💡

이미지를 한 번만 빌드하고, staging에서 확인한 그 이미지를 production에 그대로 배포합니다.

프랜차이즈의 핵심이 뭘까요? 본점과 똑같은 맛이죠. 만약 지점마다 레시피를 새로 만든다면? 맛이 달라지고, "본점에선 괜찮았는데..."라는 사고가 납니다.

배포도 마찬가지예요. staging과 production에서 같은 이미지를 써야 합니다. 커밋 SHA를 이미지 태그로 쓰면 "어떤 코드로 만든 이미지인지" 추적도 가능하고, staging에서 검증한 바로 그 이미지가 production에 올라가니 안심이에요.

이미지 한 번 빌드
# 1. CI에서 이미지 한 번만 빌드 docker build -t registry/app:a3f7c2d . # 커밋 SHA가 태그 docker push registry/app:a3f7c2d # 2. staging에 배포 → 확인 gcloud run deploy app-staging --image=registry/app:a3f7c2d ✓ staging에서 검증 완료! # 3. 같은 이미지를 production에! gcloud run deploy app-prod --image=registry/app:a3f7c2d → 본점과 지점이 100% 같은 이미지
✅ 한 줄 정리: 이미지는 한 번만 빌드, staging에서 검증한 그것을 production에 그대로.
🎲

BEFORE

수동 배포, 환경마다 다른 빌드,
"내 컴에선 되는데..."

🏭

AFTER

자동 CI/CD, 동일 이미지,
staging = production

CHAPTER 7 · 8강 & 9강

🔧 영업 중 리모델링 — 손님은 모른다

🔵🟢 손님 한 명도 안 놓치고 주방 업그레이드
💡

블루그린 배포로 트래픽 0% 배포 → 스모크 테스트 → 전환, 실패 0건으로 무중단 배포.

이게 가장 어려운 부분이에요. 영업 중에 주방을 리모델링해야 하는데, 손님들이 눈치채지 못하게 할 수 있을까요?

블루그린 배포가 답입니다. 현재 주방(블루)에서 계속 손님을 받으면서, 옆에 새 주방(그린)을 조용히 준비합니다. 새 주방이 완성되면 시식 테스트(스모크 테스트)를 하고, 통과하면 손님을 한꺼번에 새 주방으로 안내합니다. 문제가 생기면? 3초 만에 원래 주방으로 복귀(롤백)!

Cloud Run에서는 이걸 리비전과 트래픽 설정으로 합니다. --no-traffic --tag green으로 0%짜리 새 리비전을 만들고, 태그 URL로 테스트한 다음, --to-tags green=100으로 전환. 이 전체 과정을 GitHub Actions가 자동으로 해줍니다.

무중단 배포 파이프라인
# 1. 새 리비전을 0%로 배포 gcloud run deploy app --no-traffic --tag green ✓ Traffic: 0% (사용자 영향 없음) # 2. 태그 URL로 스모크 테스트 curl https://green---app-xxx.run.app/health {"status": "ok"} ✓ # 3. 전환! gcloud run services update-traffic app --to-tags green=100 ✓ 무중단 전환 완료! # 문제 시 롤백 (3초) gcloud run services update-traffic app --to-revisions old-rev=100
✅ 한 줄 정리: 0% 배포 → 스모크 테스트 → 전환. 실패하면 3초 롤백. 손님은 아무것도 모른다.
